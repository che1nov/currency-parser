# Причины деградации производительности парсера курсов валют

## Приложение

Многопоточный парсер получает официальные курсы ЦБ РФ для USD, EUR, CNY, GBP и JPY, рассчитывает изменение к предыдущему календарному дню и сохраняет данные в файловую H2 и JSON. REST API позволяет запустить сбор и получить курсы по дате и валюте с сортировкой. Автоматический сбор выполняется при старте и далее с часовой задержкой после завершения предыдущего запуска.

Технологии: Java 17, Spring Boot 3.5.16, Spring MVC, RestTemplate, JDBC/H2, ExecutorService, ScheduledExecutorService и Parallel Stream API. Архитектура — монолит: контроллер, сервисы, репозиторий и адаптеры работают в одном приложении. Для одного источника и пяти валют такое решение позволяет сохранять весь набор одной транзакцией без межсервисного обмена.

Потенциально ресурсоёмкие операции — сетевые запросы, разбор XML, запись H2 и файлов, фильтрация и сортировка результатов. Ниже приведён анализ кода версии `e94bade`: риски и способы их проверки; деградация нагрузочными измерениями в этом задании не подтверждалась.

## 1. Аппаратный уровень: сеть и дисковый I/O

**Где возможна проблема.** [CbrClient.fetch](../src/main/java/ru/study/rates/adapter/CbrClient.java) загружает два XML-документа — за выбранный и предыдущий день. Медленная сеть увеличит длительность `POST /api/collect`, а недоступность источника приведёт к HTTP 502. Медленный диск может задержать запись H2, JSON-снимка и журнала событий.

**Оценка риска.** Исчерпание сетевой пропускной способности при текущей нагрузке маловероятно: один сбор делает два запроса, XML ограничен 2 МиБ. Существеннее задержки внешнего источника. Уже заданы тайм-ауты соединения 5 с, HTTP-запроса 10 с и ожидания пары задач 15 с. Последний ограничивает только ожидание сетевых задач, а не весь POST с записью на диск. В [CollectionJournal](../src/main/java/ru/study/rates/adapter/CollectionJournal.java) запись асинхронная, но медленный диск может заполнить очередь из 256 событий и вызвать их отклонение.

**Как обнаружить.** В JMeter проверить сбор с локальной подменой ЦБ, задающей задержки и ошибки, и сопоставить p95/p99, долю 502 и длительность успешных сборов. Публичный API ЦБ нагрузочным тестом не нагружать. Через `/api/journal` наблюдать `pending`, `rejectedEvents`, `error`, через `/api/status` — `snapshotError`. Для разделения задержек добавить таймеры вокруг HTTP, разбора XML, транзакции H2 и сохранения файла. Actuator/Micrometer сейчас в проект не подключены; их можно добавить для сбора этих метрик по [механизму Spring Boot](https://docs.spring.io/spring-boot/3.5/reference/actuator/metrics.html).

**Как предотвратить.** Сохранить тайм-ауты и ограничение размера ответа. При частых повторных запросах одной даты использовать уже сохранённые курсы с явным сроком актуальности и отдельным принудительным обновлением. Для растущего `collection-events.jsonl` добавить ротацию по размеру, например 10 МиБ с хранением пяти архивов; при росте `rejectedEvents` проверять диск и частоту записи, а не увеличивать очередь без ограничения.

## 2. Контекстное переключение и число потоков

**Где возможна проблема.** Сетевые задачи выполняются в `cbr-worker-*`, расписание — в `rate-scheduler`, журнал — в `collection-journal`. Дополнительно работают потоки Tomcat, HTTP-клиента и общего ForkJoinPool для `parallelStream`. При росте числа запросов конкуренция этих потоков за CPU может увеличивать задержки.

**Оценка риска.** Риск неограниченного роста потоков сборщика низкий: в [ApplicationConfig](../src/main/java/ru/study/rates/config/ApplicationConfig.java) задан пул максимум из четырёх потоков и очередь на восемь задач. `newCachedThreadPool()` не используется. [RateCollectionService](../src/main/java/ru/study/rates/service/RateCollectionService.java) через `tryLock()` допускает один активный сбор; конкурирующий запуск получает 409. Защита сборщика не ограничивает число HTTP-запросов чтения и работу общего ForkJoinPool.

**Как обнаружить.** В JMeter постепенно увеличить число клиентов `/answer` с 10 до 50 и 150, сохраняя одинаковые паузы и параметры. Сопоставить throughput и p95 с CPU, числом и состояниями потоков в VisualVM; снять `jcmd PID Thread.print`. На Linux для прямого измерения переключений использовать `pidstat -w -t -p PID 1`. Большое число ожидающих потоков само по себе ещё не доказывает чрезмерные переключения.

**Как предотвратить.** Сохранить ограниченный пул и очередь — [ThreadPoolExecutor](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html) позволяет задавать эти пределы явно. Для текущей пары сетевых задач отдельно сравнить пул из двух и четырёх потоков; уменьшать его только при сохранении времени сбора. Не создавать поток на каждую валюту и не повышать число потоков Tomcat без измерения. Долю 409 учитывать отдельно: это отказ занятого сборщика, а не успешная обработка дополнительной нагрузки.

## 3. Алгоритмический уровень

**Где возможна проблема.** [RateRepository.findByDate](../src/main/java/ru/study/rates/repository/RateRepository.java) извлекает записи за одну дату, затем [RateQueryService.find](../src/main/java/ru/study/rates/service/RateQueryService.java) выполняет `parallelStream().filter().sorted().toList()`. Фильтрация требует O(n), сортировка — O(n log n), материализация результата — O(n) памяти.

**Оценка риска.** Сейчас `n ≤ 5`: увеличение числа дней в H2 не увеличивает размер списка за одну дату. Составной первичный ключ `(requested_date, currency)` исключает дубли. Поэтому алгоритмический риск невелик, а организация параллельной обработки может стоить дороже работы над пятью элементами. Если добавить выборку всей истории, сортировка большого списка в памяти станет отдельным риском.

**Как обнаружить.** С помощью [JMH](https://github.com/openjdk/jmh) сравнить одинаковые фильтрацию и сортировку через `stream()` и `parallelStream()` на пяти элементах, затем на синтетических 1 000 и 100 000. Данные подготовить вне измеряемого метода, результат вернуть из benchmark; использовать три fork, пять итераций прогрева и пять измерений по секунде. Сравнить время операции и аллокации через `-prof gc`. JMH проверяет обработку списка отдельно; задержку JDBC и полного `/answer` оценивать JMeter и планом SQL через `EXPLAIN`.

**Как предотвратить.** Для рабочего варианта с пятью элементами рассмотреть последовательный stream после сравнения. В учебном проекте `parallelStream` сохраняется как требование исходного задания. При добавлении истории переносить фильтры, `ORDER BY` и пагинацию в SQL, проверять план и индексы; не загружать всю таблицу ради одной страницы.

## Вывод

По анализу кода приоритет диагностики — ожидание внешнего источника и запись на диск: именно эти этапы требуют отдельных замеров. Неограниченный рост потоков сборщика уже предотвращён пулом и запретом пересекающихся запусков. Для пяти курсов усложнение алгоритма не требуется; замену параллельной обработки и изменение размеров пулов следует обосновать JMH и нагрузочным тестом.
