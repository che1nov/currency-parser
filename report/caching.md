# Кэширование: Caffeine и Redis

## Реализация

Кэшируется результат `GET /answer`: курсы за дату с выбранной валютой и сортировкой. Это подходящие «горячие» данные: одинаковые запросы повторяются, а официальные курсы за конкретную дату меняются редко. Источником данных для этого метода служит H2.

В [RateQueryService.find](../src/main/java/ru/study/rates/service/RateQueryService.java) добавлен `@Cacheable(cacheNames = "rates", …, sync = true)`. Ключ включает дату, валюту, поле и направление сортировки, поэтому разные выборки не подменяют друг друга. Пустые результаты также кэшируются и сбрасываются после сбора данных.

Оба варианта работают с одним кодом сервиса; меняется `spring.cache.type`:

| Настройка | Caffeine | Redis |
|---|---|---|
| Тип | `caffeine` | `redis` |
| Размещение | Память каждого экземпляра | Общий Redis |
| TTL после записи | 600 секунд | 600 секунд |
| Ограничение | 1000 записей | В стенде 64 МиБ, `allkeys-lru` |
| Формат | Объекты Java | JSON с заданным типом `List<CurrencyRate>` |

По умолчанию включён Caffeine, Redis для обычного запуска не требуется. [Конфигурация приложения](../src/main/resources/application.properties), [настройка JSON для Redis](../src/main/java/ru/study/rates/config/CacheConfig.java), [Docker Compose](../compose.cache.yml).

## Замеры первого и повторного вызова

Использованы Java 17.0.21, Spring Boot 3.5.16, Redis 7.4.12, H2 2.3.232, Docker и curl 8.7.1. В Docker запущены два экземпляра одного приложения с общей H2 через TCP; каждый ограничен одним CPU и 512 МиБ памяти, heap — 256 МиБ. Курсы за 05.03.2024 предварительно получены из настоящего ЦБ. Искусственных задержек БД нет.

После 15 прогревочных циклов выполнено **20 пар «промах → попадание» для каждого типа кэша**. Перед каждой парой кэш очищался; время измерялось через `curl -w '%{time_total}'` для одинакового запроса:

```text
/answer?date=2024-03-05&currency=USD&sort=rate&direction=asc
```

| Кэш | Промах, медиана, мс | Попадание, медиана, мс | Диапазон промахов, мс | Диапазон попаданий, мс | Чтений БД: промах / попадание |
|---|---:|---:|---|---|---|
| Caffeine | 2,690 | 1,911 | 2,280–3,073 | 1,683–2,212 | 1 / 0 |
| Redis | 3,314 | 2,409 | 3,096–4,901 | 2,252–2,859 | 1 / 0 |

В каждой паре счётчик реальных вызовов `RateRepository.findByDate` увеличился на один при промахе и не изменился при попадании. Содержимое ответов совпало. Время включает HTTP и соединение curl, но не запуск процесса curl; это последовательные локальные замеры, а не предел производительности под нагрузкой.

## Два экземпляра

После очистки кэшей выполнены четыре запроса: A, повторно A, B, повторно B. Дополнительные чтения общей БД:

| Кэш | Экземпляр A | Экземпляр B | Результат |
|---|---:|---:|---|
| Caffeine | 1 | 1 | Каждый экземпляр загружает собственный кэш |
| Redis | 1 | 0 | B получает запись, которую положил A |

Для Redis проверены общие ключи `currency-parser:v1:rates::…` и остаток TTL: **599 890 мс**. Для ускоренной проверки истечения оба приложения отдельно запущены с TTL 2 секунды: после ожидания 2,2 секунды следующий запрос вновь прочитал БД. Для Caffeine стандартный TTL 10 минут и лимит 1000 также проверены автоматическим тестом.

## Инвалидация

В [RateCollectionService.collect](../src/main/java/ru/study/rates/service/RateCollectionService.java) используется `@CacheEvict(cacheNames = "rates", allEntries = true)`. Очистка происходит после успешного возврата метода, когда транзакция H2 уже зафиксирована; сбрасываются все варианты даты, валюты и сортировки. Ошибка источника не очищает ранее сохранённый результат. Тест с изменением курса со 100 до 105 подтвердил выдачу нового значения после обновления.

В двух контейнерах прогреты два варианта запроса, затем выполнен повторный сбор на A. Новая метка `fetchedAt` позволила отличить обновлённую запись от старой, даже когда исторический курс не изменился:

- **Caffeine:** A получил обновлённые данные; B сохранил свою старую копию до TTL. После истечения TTL B перечитал H2 и обновился. `@CacheEvict` локального кэша действует только на экземпляр, где выполнено обновление.
- **Redis:** A очистил общий кэш, последующее чтение загрузило новые данные; B получил тот же обновлённый результат без чтения БД. Проверены оба варианта фильтрации и сортировки.

Таким образом, для нескольких экземпляров с требованием актуальности после завершённого обновления выбран Redis. Caffeine подходит для одного экземпляра либо допустимой задержки обновления до TTL; для немедленного сброса нескольких локальных кэшей понадобятся события инвалидации. Кэш и H2 не образуют общей транзакции: строгая согласованность при одновременных чтениях и обновлениях потребует дополнительного механизма версий или синхронизации.

[Исходные замеры и проверки](../results/cache/measurements.json), [скрипт воспроизведения](../scripts/measure_cache.py), [инструкция запуска](../readme.md#caffeine-и-redis--тема-6). Пройдены **44 теста**, без ошибок и пропусков.

## Вывод

Оба кэша исключили повторное чтение H2 и сократили медианное время ответа в этом эксперименте. Caffeine оказался быстрее на одном экземпляре, а Redis обеспечил общий кэш и инвалидацию между экземплярами. TTL 10 минут подходит для проверенного сценария; при более строгом требовании к свежести данных нужно уменьшить TTL и учитывать обновления во всех экземплярах, а очистку всего кэша при росте его объёма заменить адресной инвалидацией.
